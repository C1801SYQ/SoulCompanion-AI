## 二、修复清单（按严重度）

### P0 — 影响系统正确性 / 安全

#### 1. 语音事件竞态：主循环与桥接器互相"抢"语音事件
`SpeechEngine.get_latest_text()` 是**破坏性读取**（读后清空）。`main.py` 主循环和 `EmotionBridge` 都在调它 —— 谁先读到谁把事件吃掉，另一方永久丢失这条语音。
**修复**：新增非破坏性 `peek_latest_text()`（返回带单调递增 `seq` 的快照）；`launch.py` 改传 `peek_latest_text`；`bridge` 按 `seq` 去重 + 10s 新鲜度窗，避免几分钟前的一句话持续主导当前判断。
**效果**：两个消费者都能拿到完整事件流，且语音不再"越用越旧"。

#### 2. 融合引擎把"没人说话"当成一次真实的中性投票
原实现里，语音模态无论有没有输入都返回 `NEUTRAL` 并占用 0.4 权重 —— 沉默被当成了"孩子很平静"的证据，稀释真实信号（视觉 0.4 + 语音 0.4 + 环境 0.2）。
**修复**：模态无有效信号时返回 `None`，权重置零并**重新归一化**；
- 明确 `face_detected=False` 时，面部情绪读数不可信 → 视为缺失；
- 权重改为归一化后的**有效权重**（`source_weights` 之和 ≈ 1）；
- 单模态时降权 0.75（证据不足）；
- **第 2 轮补充**：白天"只有 `hour`"不再投票（此前桥接器每轮注入 `hour`，使环境通道永远投出一张 NEUTRAL 票，让上述修复对环境通道形同虚设）；`0.0` 这类合法低值读数仍正确投票。

#### 3. SQLite 写放大：每天约 17 万行
桥接器每 0.5s 一轮、每轮都 `record()` → 1 天 172,800 行，几天即可撑大数据库、拖慢趋势查询。
**修复**：`bridge._should_record()` 按 `(情绪类别, valence 档位)` 去重，仅在变化时立即写入；无变化时每 30s 补一条基线保证时间序列连续。
**实测**：恒定输入连跑 200 轮 → **1 行**；情绪剧烈波动 20 次交替 → 20 行，**无漏记**。
另外 `memory_axis._init_db()` 加 `WAL` + `busy_timeout`（看板查询不再被写入阻塞）+ 自动创建数据目录（空目录不被 git 跟踪，新克隆仓库原本会直接崩）。

#### 4. 干预冷却会挡掉安全关键干预
原 `evaluate()` **先判冷却、再生成计划**，导致 ASD 过载（`distressed`）/ 恐惧（`fearful`）这类安全关键干预会被普通 30s 冷却窗口直接吞掉 —— 对干预机器人而言这是危险的。
**修复**：改为**先算计划、后判冷却**；高紧急度（`metadata["urgency"]=="high"`）走独立的 8s 窗口；上次为高紧急度时，低优先级干预需等满 30s，避免打断正在进行的安抚。

#### 5. 安全加固（CORS / 监听地址 / 死分支）
- `allow_origins=["*"] + allow_credentials=True` 是**互斥组合**（浏览器直接拒绝），且对承载儿童情绪数据的服务过于开放 → 改为从 `config.CORS_ORIGINS` 读取，通配模式下强制 `allow_credentials=False`。
- `web/api.py` 的 `__main__` 默认绑定 `0.0.0.0`，等于把孩子的情绪看板暴露到局域网 → 改为 `127.0.0.1`，需外放时用 `--host 0.0.0.0` 显式开启。
- `/api/behavior/status` 的 `if/else` 两个分支完全相同 → 删除死分支。

### P1 — 打包 / 配置 / 可维护性

#### 6. 依赖清单残缺，项目实际上装不起来
`requirements.txt` 只有一行 `streamlit`；README 却让人 `pip install -r requirements.txt`；`launch.py` 报错提示引用 `requirements-web.txt` —— **该文件根本不存在**。
**修复**：三份清单
- `requirements.txt`：numpy(<2.0) / requests / opencv-python / onnxruntime / vosk / pyaudio / transformers / torch / pyttsx3 + `-r requirements-web.txt` + streamlit
- `requirements-web.txt`（新建）：fastapi / uvicorn[standard] / jinja2 / python-multipart
- `requirements-dev.txt`（新建）：pytest

#### 7. 配置漂移
`config.py` 只有 2 行，`main.py` 却自带一份 `Config`（含 Ollama 地址/模型/阈值）→ 两处必然漂移。
**修复**：`config.py` 成为唯一配置源（含环境变量覆盖、绝对 `DATABASE_PATH`）；`main.py` 删除自带类，改 `from config import Config, LOG_LEVEL`。
> ⚠️ **需要你确认的一处默认值**：`OLLAMA_MODEL` 默认为 `gemma3n:e4b`。原值是 `gemma4:e4b` —— 该 tag 在 Ollama 仓库中不存在（疑似手误）。若你的实际模型不同，用一行环境变量即可改回：`set OLLAMA_MODEL=你的模型`。

#### 8. 内存无界增长
`RobotState.chat_history` 只增不减，长时运行会持续吃内存 → 新增 `push_history()` 裁剪到 `MAX_CHAT_HISTORY = 200`。

#### 9. 日志刷屏 + 误导性文档 + 断掉的日报链路
- `embodied_engine` 每 0.5s 输出多条 INFO（一天约 50 万行日志），且 docstring 声称"为持续动作启动后台线程"，而 `_action_thread` 从未被赋值 → 改为诚实的"即时派发"模型、删除未用字段与未用 import（`math`/`time`）、模拟日志降为 DEBUG、仅在指令变化时输出 1 条 INFO。
- `reports/report_generator.py` 只读旧版 `logs` 表，而该表已无人写入（`core/memory.py` 未被调用）→ **日报永远是空的**。修复为优先读新管线的 `emotion_records`、回退 `logs`，并统一用情绪词表统计正/负向；数据库不存在时友好退出。
